# Phase 5 — UI Design Contract: Captura de E-mail

> Visual and interaction contract for the inline e-mail capture form. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **Scope:** UI/UX only — the visual + interaction contract of a single shared form component (`NewsletterForm`) rendered in two places. Server Action / Resend integration mechanics belong to 05-RESEARCH.md + plan tasks; this doc is the visual/interaction source of truth.
> **Inheritance law (override):** This form **INHERITS and EXTENDS** the established design system (`site/app/globals.css` `@theme` + Phases 1/4 UI-SPECs + the article-end CTA precedent). It does NOT invent a new system. Monocromático estrito (preto/branco/cinza), Anton/Montserrat, tom sereno/anti-espetáculo. Any accent hue, colored button, badge, urgency banner, or third-party widget is prohibited (REQUIREMENTS §Out of Scope, CLAUDE.md).
> **Locked decisions:** D-01..D-13 in `05-CONTEXT.md` are user-locked — this spec locks the **visual/interaction** contract around them; it does not re-open them. CONTEXT.md explicitly delegates "Design visual do bloco (espaçamento, borda, estilo do input/checkbox)" and "Copy/tom exato" to this UI-SPEC.

## Spacing Scale

Inherited from Phases 1/4 (4px base, Tailwind default), restricted to the established set. Every value is a multiple of 4. No new steps introduced.

| Token (Tailwind) | px | Multiple of 4 | Usage in the form |
|-------|-----|-----|---------------|
| `gap-2` / `mt-2` | 8 | 2·4 | label ↔ input gap; field ↔ inline-error gap; checkbox box ↔ label text gap |
| `px-4` / `py-3` | 16 / 12 | 4·4 / 3·4 | input inner padding (16 horizontal, 12 vertical → ≥48px field height) |
| `gap-4` / `mt-4` | 16 | 4·4 | input row ↔ consent row; consent row ↔ submit button; heading ↔ subtext |
| `gap-6` / `px-6` | 24 | 6·4 | **page gutter (inherited, non-negotiable)**; submit button horizontal padding (`px-8 py-4` from button precedent) |
| `pt-12` | 48 | 12·4 | section top padding above the `border-t` (matches the article-end CTA `pt-12`, D-05) |
| `mt-16` | 64 | 16·4 | gap from the WhatsApp CTA section above to the form section (matches `AuthorBlock`/`ShareBar`/end-CTA `mt-16` rhythm) |

**Container width:**
- The form section reuses the **article reading measure `max-w-[68ch]`** when inside `/blog/[slug]` (it lives in the same `max-w-[68ch]` column as `AuthorBlock`/`ShareBar`/end-CTA — D-05). On `/blog` (listing) it sits at the foot of the `max-w-6xl` container but the **form itself is constrained to `max-w-md` (~448px) centered**, so the input doesn't stretch to full listing width.
- The input + checkbox + button stack is a single centered column ≤ `max-w-md`; on `sm+` the layout stays stacked (not inline) for clarity and touch comfort — no side-by-side input+button.
- **Gutter:** `px-6` (24px) inherited at every breakpoint.

**Button geometry (inherited, non-negotiable):** submit button uses the established `px-8 py-4` + `min-h-[44px]` from the `ShareBar`/`CookieBanner`/`CTAButton` token strings.

**Exceptions:** Touch targets — the consent checkbox's clickable area (the whole `<label>` row) and the submit button are each ≥ **44×44px** (inherited a11y floor — a fixed accessibility minimum, not a spacing step). The input field min-height is 48px.

Display = **Anton** (always `uppercase`, weight 400). Body = **Montserrat** (weights **400 / 600 only**). The form touches **3 of the 4 inherited semantic sizes** (no Display-tier 36px needed — this is a calm sub-block, not a hero; the section heading is Heading tier, deliberately quieter than an article H1). Hierarchy beyond size comes from font/weight/case/margin, never a 5th size.

The submit button label is uppercase because that is the inherited button typography (`CTAButton`), not authored hype.

## Color

Inherited monochrome system — **no new color tokens, no accent hue, no red.** The "10% accent" is **pure white reserved for action/emphasis** on the black ground, exactly as Phases 1/4 defined.

| Role | Token | Value | Usage in the form |
|------|-------|-------|---------------|
| Dominant (~60%) | `--color-bg` | `#0a0a0a` | The section ground — same page ground as the article/listing. The block is set off only by `border-t border-line`, not by a different background. |
| Secondary (~30%) | `--color-surface` / `--color-line` | `#141414` / `#262626` | **Input field fill** (`bg-surface`), checkbox box outline, the `border-t` section divider, default input/checkbox borders (`border-line`). This is the form's quiet structure. |
| Accent (~10%) | white | `#FFFFFF` / `--color-fg #ededed` | **Reserved for:** the solid submit button (white fill, black label — the form's single emphasis); the section heading (Anton on black); input/checkbox **focus** border (`border-fg/40`) and the inherited white focus-visible ring; the `/privacidade` inline link on hover (`text-fg`); the success heading. Nothing else competes. |

**Text tokens (inherited — pick by background):**

| Token | Value | Context | Contrast |
|-------|-------|---------|----------|
| `--color-fg` | `#ededed` | Primary text on black: heading, typed input value, error text, consent label, button label-on-white (`text-bg`) | ~15:1 — AAA |
| `--color-muted` | `#7f7f7f` | Secondary on black: subtext, placeholder, success body | ~4.7:1 — AA, **do not alter** |
| `--color-fg-on-light` / `text-bg` | `#0a0a0a` | Submit button label inside the white button | ~19:1 — AAA |

**Destructive / error color: NONE.** This is the load-bearing color decision of the phase. The form has **no red, no destructive hue** — a red error token would violate "monocromático estrito" (REQUIREMENTS §Out of Scope: "Cor de destaque … CTA colorido"). **Error states are signalled by structure, not color:** (1) inline error text in `text-fg` (`#ededed`, white — high contrast, AA+), prefixed by a short bold lead word; (2) the offending field/checkbox gets a `border-fg` (white) outline instead of `border-line`; (3) `role="alert"` + `aria-live` carries it to screen readers; (4) focus is moved to the field. Color never carries error meaning alone (WCAG 1.4.1 — and here there is no error color at all). Submitting is **not** a destructive action — no confirmation dialog, no destructive styling.

**Accent reserved for (explicit, never "all interactive elements"):** the single white submit button · the section heading (Anton) · the input/checkbox focus border + white focus-visible ring · the `/privacidade` link hover · the success heading. The input fill, the checkbox box, dividers, subtext, placeholder, and error text are NOT accent.

## Accessibility Contract

LEAD-02 makes a11y a hard acceptance criterion. This contract is consistent with the a11y rigor of Phases 1/3/4.

- **Contrast:** heading/typed value/error/consent label `--color-fg` on `--color-bg` ~15:1 (AAA). Subtext/placeholder/success body `--color-muted` ~4.7:1 (AA, do not alter). Submit button label `#0a0a0a` on white ~19:1 (AAA). All AA+. No text relies on a color hue (there is none).
- **Labels:** the email input has a **visible** `<label htmlFor>` (never placeholder-as-label). The checkbox is wrapped in / bound to a `<label>` whose text is the consent statement, including the inline `/privacidade` link.
- **Focus indicators:** inherited `:focus-visible` white ring on input, checkbox, `/privacidade` link, and submit button. Never reset outline without the white-ring replacement; never the browser-blue default-only.
- **Managed focus (D-08/D-10/D-13):** consent error → focus to checkbox; invalid email → focus to input; success → focus to the success panel (`tabIndex={-1}`). Focus never gets lost when the form is replaced by the success panel.
- **`aria-live` (D-13):** field/consent/server errors via `role="alert"` `aria-live="assertive"` (interrupts — the user needs to know now). Success via `role="status"` `aria-live="polite"`. The form sets `aria-busy="true"` while pending.
- **`aria-invalid` + `aria-describedby`:** each errored field is `aria-invalid="true"` and points to its error region's stable `id`.
- **Keyboard:** full keyboard path — Tab to input, Tab to checkbox (Space toggles), Tab to submit (Enter/Space submits). Enter inside the email input submits the form (native). Whole-row checkbox label is clickable (≥44px).
- **Targets:** input ≥48px tall; checkbox row + submit button ≥44×44px.
- **`prefers-reduced-motion`:** any pending spinner and the button hover-scale are gated off (the global media-query reset + `usePrefersReducedMotion()` already cover this). Content/state changes remain instant and complete.
- **Privacy / no dark pattern:** checkbox **unchecked by default** (D-07) — opt-in is a real choice, never pre-ticked. Already-subscribed shows the same success without leaking that the address existed (D-11).

## Copywriting Contract

Tom **sereno, íntimo, direto, anti-espetáculo** (`brand/tom-de-voz.md`). The e-mail is the *soft* conversion; the WhatsApp CTA above is the *strong* one (D-06) — so this copy is calm and low, never a second sales pitch. **Hard prohibitions** (brand law, checker validates): no "não perca" / urgency / scarcity / timer language; no "inscreva-se já", no exclamation/caps in the voice; no privacy-cliché ("prometemos não enviar spam", "fique tranquilo", "odiamos spam tanto quanto você"); no promise of cadence/frequency/result (NEWS-01 is deferred — this phase only *captures*); no "newsletter" hype framing. Second person ("você"). The word **"direção"** is reserved (peso máximo) — use it sparingly and on-brand.

Below is the **prescribed v1 copy** (executor may refine wording within the same register per CONTEXT's discretion, but these are on-brand, ready-to-ship, and the defaults of record):

| Element | Copy (pt-BR) |
|---------|------|
| **Section heading** (Anton, uppercase) | `RECEBA A DIREÇÃO NO SEU E-MAIL` — calm, on-brand, no urgency, no "assine"/"inscreva-se". Uses the reserved word once, with weight. |
| **Section subtext** (Montserrat, `text-muted`) | `De vez em quando, um princípio do método direto para você. Sem ruído.` — sober, sets the soft expectation without promising cadence or "spam-free" cliché. |

- **CAPTCHA / third-party anti-bot widget** — prohibited (injects external UI/script/color). Honeypot / basic rate-limit in the Server Action is allowed but is **not a UI element** (invisible to the visitor; not specced here — see plan/threat-model).
- **Colored error/destructive state, any accent hue, badge, shadcn/registries** — prohibited by brand law / not initialized.
