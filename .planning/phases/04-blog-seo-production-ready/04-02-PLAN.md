<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MDX frontmatter → build | Untrusted/invalid frontmatter (esp. once Phase 6 generates it) crosses into the build pipeline |
| JSON-LD object → HTML `<script>` | Structured-data string injected into the rendered page |
| env var → metadataBase/URLs | `NEXT_PUBLIC_SITE_URL` flows into all absolute URLs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-02 | Tampering | frontmatter validation bypass (BLOG-01) | mitigate | zod `safeParse` THROWS inside the build-time loader (Task 1); a missing/invalid field aborts `next build` — no page ships without `description`/`date`. |
| T-04-03 | Information Disclosure / XSS | JSON-LD serialization | mitigate | `JsonLd.tsx` applies the mandatory `.replace(/</g,"\\u003c")` scrub before injection (Task 2); all later JSON-LD passes through this one primitive. |
| T-04-04 | Spoofing | SSRF/URL handling in canonical/OG base | accept | `NEXT_PUBLIC_SITE_URL` is a build-time, developer-controlled env var (not user input); no runtime fetch of the value. Low risk; documented fallback. |
</threat_model>
